# 監査付き状態digestとretention checkpoint

共通監査のrecord codec v2は、`scope`と`resource_id`に結ぶ`resource_digest`を署名する。`verifyAuditState`はcheckpointから現在のDB外CAS anchorまで全chainを検証し、各集約状態の最新digestと、その根拠となる共通sequenceを返す。Web専用のsequenceや別の信頼rootは作らない。

`AuditRepository.readVerifiedState`は検証したSQLite snapshot内で読み取りを実行する。`appendPrepared`と`ApprovalTransaction.runPrepared`は同じwriter snapshotの検証済み状態を事前判定へ渡す。callbackへ渡すanchor・binding・scopeは凍結し、frameworkの検証根拠をcallbackから変更できない。repositoryの呼出側は、同じconnectionで読んだ実metadataをcanonical化し、そのdigestを対応するcommitmentと必ず照合する。digestが署名されているだけでは、任意の業務rowを認証したことにならない。欠落・不一致・scope違いはfail closedにする。

retentionはcodec v2のcheckpointへ、削除境界時点の各集約状態の最新commitmentを引き継ぐ。削除対象の単一recordだけでなく、現在のexternal anchorまで全chainが検証できた場合だけcheckpointを署名する。残すrecordの本文・MACは変更しない。後続のv2 recordは同じscope/resourceのcommitmentを更新し、他のcommitmentは維持する。400日保持、外部CASのreserve、DB commit、finalize、検証後のprefix削除という順序を維持し、応答不明時に再送しない。

状態rootは最大64件で、個別job・session・principalの件数をこの上限に対応させない。Web認証状態や共通承認状態など、別途boundedなmetadata集約に使用する。65件目のrootを追加するrecordはanchorの予約前に拒否する。これは保存容量の上限であり、古いprincipal indexや監査根拠を自動削除する許可ではない。

opt-in audit schema v2はcheckpoint JSONの容器を4 KiBから64 KiBへ拡張する。既知のv1 DDLとversionだけをtransaction内で移行し、checkpoint、record、transactionの既存値を保持する。未知・部分schemaは修復しない。既存のv1 checkpointとrecordのchainは検証可能だが、非genesisのv1 checkpointでは過去に削除された状態rootの完全性を保証できない。この場合、状態読取・更新の事前判定・v2 checkpointへのretentionをfail closedにし、空のroot集合として引き継がない。schema移行だけでは不明な状態を再確立しない。v1 genesisから全履歴が残るchain、または既存v2 checkpointからのchainでは、新しいretentionにv2 checkpointを使用する。Dispatcher本体のruntime migration、readiness、DB外providerのprovisioningやrepairは、このopt-in installerへ含めない。

追加検証は、v1 schemaからの保存内容を保持した移行、scope分離、複数回のretention、suffixを含むchain破損、commitmentの欠落・改変、業務rowの旧値への差替え・削除、callbackのwrite/async拒否、最大長rootと容量上限を対象とする。fixtureのanchor/keyは実運用のrollback耐性やcredential storeの証拠ではない。#16のbroker・public repository・runtime接続と#141のWeb状態保存は継続事項である。
