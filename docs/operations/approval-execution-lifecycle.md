# Approval executionの状態broker

`ApprovalExecutionBroker`は#16の内部状態遷移を扱います。実Slack送信やpublic APIを提供せず、実authority/proof providerを接続した完成runtimeではありません。requestの`consumed`とattemptの`executing`・`succeeded`は別の状態です。

## 開始

入力はopaqueなattempt handle、authority ref、expected fenceだけです。trustedな同期authorityが同じVerifiedAuditState内で認証済み内部executor、current binding/policy、requester membership、supervisor visibility、shared状態、ordered threadを含むsnapshotを照合します。client由来のactor・outcome・receiptを採用しません。

brokerは保存済みrequest/decision/consume/attemptの共有root、clock履歴、開始期限、attempt payloadのownerとsemantic/content binding、保持鍵での本文復号を検証します。期限切れ・precondition不一致・利用不能な本文は外部callなしでneeds_reviewと本文削除へ収束します。

成功時はclaimedからexecutingへ進め、fence増分とcurrent markの用途別markerを同じ監査transactionへ保存します。audit finalizeまで確認して初めてstartedを返します。本文やmarkerをAPI responseへ返しません。既存executing/unknown/terminalに再度startしても、新しい実行権限を作りません。

このstarted結果をserializableな送信許可として公開してはいけません。#21のclosed workerが、fresh start成功と一度だけの送信をprocess内capabilityで結び、外部call直前のdeadline/current authorityとexact marker不在の全page確認を行う必要があります。このworkerは未接続です。

## 結果と復旧

結果入力にもoutcomeやreceiptは含めません。mandatoryなreceipt authorityが、保存markerへ結合した認証済み送信応答またはread-only reconcile proofから結果を導出します。callbackとreconcileは別のproof kindで、current fenceへ一致する必要があります。

executingを復旧した場合は必ずacceptance_unknownへ進め、fenceを増やして古いcallbackを無効にします。0件の観測はunknownのまま維持し、同じwriteを再送しません。reconcileで一意に確認したacceptedまたは決定的rejectionだけをsucceeded/failedへ進めます。複数または不完全なproofはneeds_reviewへ進めます。曖昧な送信応答自体からはまずunknownへ進みます。

succeeded/failed/needs_reviewの結果metadataとattempt本文の削除は同じrecord/payload/history transactionへ保存します。本文保持は最大24時間です。期限切れexecutingの復旧もまずunknownと本文削除を同時保存し、次の復旧処理でneeds_reviewへ収束します。二段階の間に停止しても本文は保持せず再送を許可しません。sweep workerはこのdurableなunknownを次回回収する必要があります。requestはconsumedのまま保ち、terminal attemptを再実行可能に戻しません。SQL失敗はrollback、audit応答喪失はread-only照合の対象で、blind retryは行いません。

## 検証境界

fixtureでは開始と重複、認証/scope/fence、current precondition、本文・鍵、期限、結果と削除、復旧・旧callback拒否・reconcile、SQL/audit障害と再openを検証します。fixture authorityの文字列は認証機構ではありません。実consumer認証、外部proofの収集、Slack全page scan、配送worker、protected credential store、operator admission、runtime activationは後続の接続と検証が必要です。
