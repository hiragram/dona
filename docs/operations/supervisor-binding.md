# supervisor bindingの保護境界

Issue #17の内部部品。承認機能全体のproduction activationやSlack interactive endpointを追加しない。

## 保存とoperator操作

`installApprovalSupervisorBindingSchema`は既存v5からv6へ明示移行し、同じSQLiteの`approval_supervisor_bindings`を追加する。初期binding、Keychain item、監査rootを自動作成しない。`SupervisorBindingOperator`は共有の保護時計・audit transactionへbinding digestをcommitする。読み取りではSQLite行、監査resource root、DB/backup外の保護generationをrevision、digest、transaction IDで照合する。どれかが欠落・不一致ならfail closedする。

operator専用経路は、別のoperator identityとcredential domainに結合した二人のproofを、対象のaction、次revision、proposal digest、transaction IDへ固定して渡す。proofのdigestとoperator IDをbindingへ記録し、監査chainがその行を認証する。同じ人・credential・domainの再利用は拒否する。通常event/MCP入力からこのserviceを呼び出さない。

`KeychainBindingGenerations`は既存のnative Keychain CAS protocolの`binding_generation`用途を使う。instance/workspaceからKeychain scopeを導出し、operatorが別途用意したgenesis値を初回CASでだけgeneration 1へ進める。CAS応答喪失、DB commit前の障害、restore mismatchではgenerationを戻さずapproval経路を停止する。自動retryやDB行からのgeneration再作成はしない。

## requestのcurrent確認

v6のcreate、approval card配送、decision、consume、execution startは`SupervisorBindingGuard`必須。移行前に構築したbrokerも、v6移行後はguardなしの新規操作を拒否する。guardはbrokerのinstance/workspace scope、同じ監査stateのbinding ID/revisionと、trusted adapterが取得したcurrent access receiptのinstance、workspace、alias、team、user、permission、target visibility、shared状態、phase、transaction ID、時刻を照合する。receiptは30秒以内かつ期限前だけ有効。Slack側の`SlackApprovalAccessProbe`は現行workspace registryでalias/teamを照合し、user状態、非shared channel、bot membership、supervisor membershipを現在のAPI結果で確認する。DMではconversationの`is_member`省略を許すが、supervisorのmembershipはAPIで確認する。通常channelでは共有状態の全flagが明示された場合だけ許可する。取得不能やpage不完走は拒否する。`signSlackApprovalAccessObservation`は専用の32 byte Keychain鍵と鍵versionで観測をHMAC認証する。`bindSupervisorAccessObservation`はMACを定数時間で検証した上で、operation、target、phase、transaction IDを同じscopeへ結び直す。鍵配布と認証済み内部通信の接続は別途必要であり、観測DTO自体を外部入力から受け取って認可証明にしない。

rotation/revoke/break-glassでrevisionが進むと、旧revisionのpending/approved requestは各brokerで承認・consume・実行できなくなる。createの同一source再試行でも保存済みbindingを照合し、旧requestを`needs_review`へ収束させる。接触したrequestは共有record/payload mutationで`needs_review`へ収束する。監査済み旧requestの表示状態が直ちに更新されたことや、未知の配送済みcardが削除されたことを意味しない。presentationの後続更新は既存outbox規則に従う。

break-glassは最大30分、理由、二者proof、operation/target digestを必須とする。期限・scopeは各段階で直接照合し、期限切れの一時bindingから元の恒久bindingへ自動復帰しない。新しいoperator操作を要する。

## 接続条件

このbranchには、Slack側の観測をDispatcher内の認証済みtransaction/phase/operation/target receiptへ搬送する接続、local operator本人確認UI、Keychain itemのoperator provisioningは存在しない。これらがない状態でv6 approval経路を有効化しない。testのin-memory proof/Keychain transportは本番の認証・永続性の証拠ではない。
